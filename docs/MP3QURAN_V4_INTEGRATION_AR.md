# MP3Quran API v4 — تكامل التلاوات في خزائن الهدى

## نطاق التكامل

أُضيفت شاشة `/quran/recitations` من فهرس القرآن أو صفحة فهرس الأقسام. تتيح البحث عن القارئ بالعربية أو اللاتينية، تصفح تلاواته، اختيار الرواية/النمط، عرض السور الموجودة في `coverage.surahs`، وتشغيل سورة من `files.original.url` الذي تعيده نقطة تفاصيل السورة.

عنوان الخدمة المستخدم هو `https://api-staging.mp3quran.net/v4`. هذه بيئة Staging وقد تتغير واجهتها أو بياناتها قبل الإصدار العام؛ لذلك عُزل عنوان API في مستودع مستقل ولم يُخلط مع API الخادم المحلي.

## الهوية والبيانات

- يحتفظ التطبيق بـ `reciter.code` و`recitation.code` فقط، مثل `mahmoud-husary` و`mahmoud-husary/r1`.
- لا يخزن التطبيق `id` الرقمي الوارد في استجابات الخدمة؛ تُحذف الحقول الرقمية `id` من موارد القراء والتلاوات قبل وضع الاستجابة في ذاكرة ETag المؤقتة.
- تُستخدم `GET /v4/recitations/{code}/surahs/{n}` لجلب رابط سورة واحدة؛ لا يُنشئ العميل رابط ملف منفرداً بالتخمين.
- عند تجهيز عدة روابط، يقرأ العميل `audio.base` و`audio.files.original` من مورد التلاوة، ويستبدل `{surah:03d}` برقم السورة بثلاث خانات.
- قوائم القراء والتلاوات تتبع `links.next` حرفياً دون إعادة بناء مؤشر الصفحة. تتبع قائمة التلاوات جميع الصفحات قبل عرض اختيار التلاوة.

## التخزين المؤقت والأخطاء

تُحفظ استجابات JSON ووسوم ETag في مجلد دعم التطبيق. يرسل العميل `If-None-Match` عند إعادة التحقق، ويعيد جسم الاستجابة المحفوظ عند HTTP 304. لا يؤدي فشل كتابة الذاكرة المؤقتة إلى تعطيل التشغيل المتصل.

تُقرأ أخطاء API من `error.code` و`error.message` و`error.field`، مع التعامل المميز مع `not_found` و`audio_missing` و`invalid_parameter` و`unknown_parameter` و`validation_failed` و`rate_limited` و`queue_full` و`internal`. عند HTTP 429 أو 503، ينتظر العميل عدد الثواني الوارد في `Retry-After` ويعيد المحاولة بحد أقصى مرتين بعد الطلب الأول.

## التوقيتات

تُقرأ توقيتات الآيات من `[ayah, start_ms, end_ms]`، مع إبقاء `ayah=0` للبسملة و`ayah=-1` للاستعاذة. وتُقرأ توقيتات الكلمات من `[ayah, word_position, start_ms, end_ms, occurrence]` دون فرز أو إزالة تكرارات؛ لأن ترتيبها هو ترتيب السماع، وقد يظهر موضع الكلمة أكثر من مرة مع قيمة `occurrence` مختلفة.

تعرض الشاشة التوقيتات في قائمة مستقلة وتذكر أنها آلية وقد تخطئ، وقد يصل الفرق إلى نحو 50ms. لا تُستخدم هذه التوقيتات لإعادة كتابة نص المصحف أو استنتاج نص غير موجود.

## حدود الحقوق والتوزيع

يوضح توثيق MP3Quran v4 كيفية تشغيل رابط `files.original.url` عبر مشغل صوتي، لكنه لا يثبت بمفرده ترخيص كل تسجيل صوتي لإعادة التنزيل أو التخزين أو إعادة التوزيع. لذلك:

- التشغيل متصل من رابط HTTPS الذي يعيده المصدر فقط.
- لا ينزّل التطبيق ملفات التسجيلات ولا يضمّنها ضمن APK ولا يعيد استضافتها.
- لا يُفعّل التخزين المؤقت للصوت أو التشغيل دون اتصال.
- حالة المصدر في سجل المصادر هي `api_streaming_only_rights_review_required`، وليست إقراراً بترخيص إعادة التوزيع.

## الوثائق والتحقق

تمت مراجعة صفحة مرجع MP3Quran v4 الرسمية المفهرسة، بما فيها Quickstart وPlay audio وSync with timings وConventions، واستخدمت أمثلتها لتحديد أشكال البيانات والمسارات. تعذر جلب `https://docs-staging.mp3quran.net/llms.txt` وملف OpenAPI الخام `https://api-staging.mp3quran.net/v4/openapi.json` مباشرة من بيئة التطوير (أخفق الاسترجاع المباشر)، لذلك لا أدّعي أن هذين الملفين الخامّين قُرئا أو أن النماذج مولدة منهما. قبل ترقية التكامل من Staging إلى الإنتاج، ينبغي مطابقة كل المسارات والحقول مع `llms.txt` وOpenAPI الخام عند إتاحة الوصول. كما أن وصف المستخدم لمهمة البناء انتهى بعنصر نائب (`<describe what you are building>`)، لذا فُسّر المطلوب بالاستناد إلى سياق مشروع خزائن الهدى على أنه إضافة فهرس قراء وتلاوات القرآن وتشغيل السور وعرض توقيتاتها.

الاختبارات المضافة تغطي ترميز الأكواد، قالب الصوت متعدد السور، رفض مضيف صوت خارجي، ترتيب توقيت الكلمات والتكرار، وعلامتي البسملة والاستعاذة. فحوص Flutter/Dart تحتاج SDK مثبتاً؛ فحوص الخادم لا تغني عنها.
